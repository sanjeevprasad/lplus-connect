## Why beto-rust and not `google/ukey2` master

`google/ukey2` `src/main/proto/` is the canonical origin but is *older*:

- `ukey.proto` there lacks `Ukey2ClientInit.next_protocols = 5` and
  `Ukey2ServerInit.selected_next_protocol = 5` (v2 next-protocol fields we
  generate and leave empty — the phone never sends them either).
- `securemessage.proto` there lacks `EncScheme::AEAD = 4`,
  `SigScheme::AES_256_GCM_SIV = 3`, and `Header.nonce = 8`; instead it has
  `HeaderAndBodyInternal { required bytes header = 1; required bytes
  body = 2 }` — Google's own RawHAB packing, which beto-rust dropped. If
  the dormant `d2d::signcrypt` path ever needs the raw-bytes header again,
  that message is the upstream-blessed shape.
- `securegcm.proto` there is the full cloud-registration set
  (`GcmDeviceInfo` etc.); beto-rust keeps only `GcmMetadata`, which is all
  the LAN stack uses.

`device_to_device_messages.proto` differs from upstream in comments only.

Also available upstream if a lane ever needs it (not vendored, not used):
`google/ukey2` `passwordless_auth_payloads.proto`,
`proximity_payloads.proto` (Fast Pair). Nearby SecureGroup protos live in
Google's networked-transports Gerrit, not here.

## Oplus-side messages — where the source is NOT

There is no ColorOS/OnePlus source release covering the connectivity stack:
the OSS releases (OnePlusOSS GitHub, open.oppomobile) are kernel + HAL only.
`ScpMessage`/`Hello`/`SyncData`/`SyncSecure` (`src/scp.rs`) and the
`oplus.proto` fork were reconstructed from the phone's generated
protobuf-lite classes and re-verified against `com.heytap.accessory`
AccessoryFramework.apk on a live device — see the header comment of
`src/scp.rs` for the exact `*_FIELD_NUMBER` corroboration.

### The authoritative .proto does exist — privately

The Windows daemon `devicespace.exe` (winzip/daemon, PC-side engine) embeds
cargo paths of Oplus's private Rust repo **`connect-protocols`** (git rev
`c7a96db`, e.g. `connection/src/protocol/scp_packet/packet_builder.rs`)
plus its prost field-name pools, which give the original definitions:

- `Ukey2ClientInit{random, cipher_commitments, next_protocols,
  next_protocol}`, `Ukey2ServerInit{selected_next_protocol}`,
  `Ukey2ClientFinished{iv_spec}` — same newer ukey.proto as the beto-rust
  copies vendored here, plus the `iv_spec` fork
- `ScpWrapData{msg_type, …}`, `ScpHelloData{sequence_no, namespace, …}`,
  `ScpSyncData{custom_data, key_type, link_type, active_trigger_mode,
  model_id, …}`, `ScpSyncSecure{ksc, ksc_alias, …}`,
  `ScpDisconnectData{disconnect_code, disconnect_reason}`
- `ScpMessageType` variants: Hello, Sync, SyncSecure, Ukey2Init,
  Ukey2Finished, OobkeyBuild, OobkeyProcess, OobkeyFinished
- `pantaChannelService.exe` carries the C++ side: `ukey.proto`,
  `securemessage.proto` (package `securegcm`, full protobuf)

If `connect-protocols` ever surfaces publicly, re-vendor these as .proto
files and retire the hand-tagged structs in `src/scp.rs`.

### Extracted descriptors (oracle, not build input)

Oplus compiled full C++ protobuf descriptors into
`pantaChannelService.exe` (PC daemon); their serialized
`FileDescriptorProto`s were located in `.rodata` at the `\n\nukey.proto` /
`\n\x13securemessage.proto` field-1 tags and parsed with
`google.protobuf.descriptor_pb2.FileDescriptorProto`. The dumps are NOT
checked in — they derive from a proprietary binary (no license grant) and
are strictly *older* than the vendored Apache files; we deliberately do
not generate from them. To re-derive: scan for those tag+name offsets in
the exe and parse the largest valid prefix at each. Findings:

- Their `ukey.proto` = old `google/ukey2` base + `Ukey2ClientFinished.ivSpec
  = 2` (camelCase, wire tag 2 = our `oplus.proto` `iv_spec`). No
  `next_protocols`/`selected_next_protocol` — our beto-rust copy is the
  superset, which prost handles (fields left empty).
- Their `securemessage.proto` = old official: `Header` with **official tag
  layout** (enc=2, iv=5, public_metadata=6) — independent confirmation of
  the 2026-11 decision to use the official `Header` in `src/d2d.rs` — and
  `HeaderAndBodyInternal{bytes header, bytes body}` (Google's RawHAB) that
  beto-rust dropped. No `AES_256_GCM_SIV`/`AEAD`/`nonce`; our superset
  again safe.
